# Vantage

An observability platform written from scratch in Rust: a time-series store, a
PromQL-compatible query engine, a log store with a LogQL-shaped query language,
dashboards with template variables, twelve visualisations, and an alerting
engine with a real state machine.

It covers the ground a Prometheus-and-Grafana stack covers — a store, a query
language, dashboards, Explore, alert rules with a state machine — but as one
desktop program rather than a cluster of services. None of it is derived from
those projects' code: the storage engine, the query evaluator, the regex engine
and the alerting are written from scratch here, and every place the behaviour
deliberately differs is documented in the design notes below.

There is no server: storage, querying, alert evaluation and rendering all
happen in one process, against a simulated infrastructure the program generates
for itself. The one thing that reaches the network is a Prometheus source you
configure: it is scraped on its interval with a plain HTTP GET written in this
crate, and its samples become queryable series. Nothing else is ever sent, and
no HTTP library was added to do it. The dependency tree is not quite as bare as
the program, because the GUI toolkit brings the platform's own windowing,
clipboard and accessibility clients with it; `SECURITY.md` names them and says
what they talk to.

```
cargo run --release                 # open the desktop application
cargo run --release -- --report     # generate the estate and print a summary
cargo run --release -- --paths      # where this installation keeps its files
cargo test                          # 565 tests

# State, logs and exports live under the user profile by default.
# `--config-dir DIR` puts them somewhere else, which is what a portable or
# managed install needs.
```

## What is in here

| Layer | Module | What it does |
| --- | --- | --- |
| Storage | `tsdb`, `model` | Labelled series, sorted samples, label indexes, retention, staleness |
| Query | `promql` | Lexer, precedence-climbing parser, evaluator: 43 functions, 11 aggregations, 15 operators, subqueries, vector matching |
| Regex | `regexlite` | A backtracking engine with capture groups, so label matchers and `label_replace` work without a dependency |
| Logs | `logs` | Stream selectors, line filters (`\|=`, `!=`, `\|~`, `!~`), level filters, volume histograms |
| Data | `simulator` | Seven hosts, thirteen metrics, cumulative histograms, log streams, and one incident |
| Panels | `panel`, `transform` | Field configuration, thresholds, twelve visualisations, eleven transformations |
| Dashboards | `dashboard`, `variables` | A 24-column grid that never overlaps, six kinds of template variable, chained resolution |
| Alerting | `alerting` | Rules, `for` durations, per-label-set instances, contact points, routes, silences, history |
| Admin | `admin`, `datasource` | Users, teams, roles, API keys, plugins, data sources with honest health checks |
| Network | `net`, `scrape` | A hand-written HTTP/1.1 `GET` and the Prometheus text scraper that reads a configured target into the store |
| Persistence | `persist` | Versioned JSON, atomic writes |
| Interface | `app/*` | egui: nine screens, a panel editor, Explore, and the alerting console |

## Design notes

**The query engine evaluates point by point.** A range query runs the whole
expression independently at each step and stitches the results by label set,
which is what Prometheus does. Every operator therefore has a point-in-time
definition, and a per-query selector cache removes the cost of re-reading the
store at each step.

**`rate` does not extrapolate.** Prometheus scales a partially-filled window up
to its full width; this divides by the span the samples actually cover. The two
agree on evenly-spaced data and differ on the first window after a target
starts. The choice is documented next to the code.

**NaN means "no data", and never zero.** A sample that is NaN is left out of
an aggregation rather than poisoning it, so `sum` over a group where one target
stopped reporting is the sum of the targets that did. Prometheus instead
propagates the NaN and answers NaN for the whole group. The rule holds across
the whole list, which is the part that is easy to get wrong: `sum_over_time`
excludes NaN exactly as `avg_over_time` and `min_over_time` do, and `count`
counts the members that reported rather than the members that exist, so
`sum(x) / count(x)` is `avg(x)` and `sum_over_time / count_over_time` is
`avg_over_time`. `group()` is the operator that answers "is anything here at
all". The one case where this and Prometheus must agree is an empty result: when
*every* member of a group is NaN there is nothing to add up, and every
aggregation here — `sum` included — answers NaN, which a panel renders as `-`.
Reporting `0` there would tell you a fleet served no errors when in truth it
reported nothing at all.

**NaN sorts last, in both directions.** `topk`, `bottomk`, `sort` and
`sort_desc` order by value and put the targets that reported nothing after the
ones that did. Comparing floats with `partial_cmp` and calling an incomparable
pair equal is not a total order: it leaves NaN wherever the store happened to
put it, drags the values around it out of order, and past a few thousand series
makes the standard library's sort panic. A "top five by error rate" must not be
able to answer with a host that reported nothing.

**The staleness window is left-open.** An instant lookup reaches back over
`(t - 5m, t]`, so a sample exactly one lookback old has expired rather than being
the last usable reading, and two evaluations a lookback apart cannot both claim
the same sample. Range selectors are left-open for the same reason.

**Quantiles outside [0, 1] are infinities, not clamps.** `quantile(1.5, ...)`
and `histogram_quantile(-0.5, ...)` answer +Inf and -Inf as Prometheus does.
Clamping to the maximum or minimum would return a number that looks like a
measurement and hide the typo that produced it.

**Recursion over untrusted text is bounded by depth, not only by time.**
The regex matcher and the PromQL parser both recurse, and running out of stack
aborts the process — it is not a panic and cannot be caught, so nothing would be
saved on the way down. Both carry an explicit depth limit, and the matcher counts
repeats of a single character rather than recursing through them, so `.*` over a
log line of any length stays flat. Where the matcher does give up, the log
filters report it as an error: answering "no match" would be silently wrong for
`|~` and silently *inverted* for `!~`.

**Panels are cached by signature.** The cache key covers the interpolated query
text, the step-aligned window and a data version counter, so changing a variable
invalidates it but a relative time range does not thrash it sixty times a
second.

**A Prometheus source is read, and anything else says it is not.** A Prometheus
source is scraped on its configured interval, its samples stored under `job`
and `instance` labels - `up` included, so a remote target is covered by the
seeded "Target down" rule - and only the series scraped from a source answer
when a panel is pinned to it. Loki, Postgres and the rest can be configured,
but their health check reports that this build has no connector for them rather
than returning a green tick that means nothing.

## What it scales to

`cargo run --release --bin bench` measures this; the table is its output, and
re-running it is how a change to the evaluator is judged. Each figure is the
fastest of five runs — every source of noise on a desktop makes a run slower and
none makes it faster, so the fastest run is the closest estimate of the cost.

One query over a six-hour window at 400 steps:

| Series | `rate(...[5m])` | Per series |
| --- | --- | --- |
| 100 | 7 ms | 69 µs |
| 1,000 | 88 ms | 88 µs |
| 5,000 | 523 ms | 105 µs |
| 20,000 | 3.9 s | 197 µs |

These are the fastest of twenty-five runs on one desktop machine, and they are a
measurement of that machine as much as of this program: the same commit measured
about 1.6× faster on the machine and toolchain the previous table was taken on.
Use them for the shape rather than the absolute — and if a change to the
evaluator is being judged, measure before and after on one machine rather than
against the numbers printed here.

A dashboard of eight panels is comfortable to roughly 8,000 series and sluggish
past that; the demo estate is 147.

The per-series column is the interesting one. It climbs with the estate — about
70 µs at a hundred series and about 200 µs at twenty thousand — and most of that
is not the evaluator doing more work. Twenty thousand series of samples are
220 MB, so every lookup misses cache. Reading the store is not the problem:
selecting all five thousand series over six hours takes 7 ms of the 523.

Two things keep the rest honest, both of them the result of measuring rather
than guessing. A label set stores its own content hash, because keying the
result map by label set hashes four keys and four values two million times in
one query, which a profiling run at the time put at 47% of that loop. And a
window reduction such as `rate` borrows its samples from the per-query selector
cache instead of copying each window into a fresh `Series`: the same run counted
the copy as eight million allocations for a twenty-thousand-series graph.
Neither of those two figures comes from `bench` and neither can be reproduced
with it — it times whole operations with a clock and measures nothing finer, so
what it can show about these two changes is the wall-clock row above.

## Packaging

The Windows executable is built for the windowed subsystem, so no console
appears beside it, and carries its icon and a version resource — product name,
version and copyright — which is what Explorer, software inventories and
SmartScreen read. `--version`, `--report` and `--paths` still print when they
are run from a shell.

Releases are built by `.github/workflows/release.yml` on a `v*` tag, for three
targets: `x86_64-pc-windows-msvc`, `x86_64-unknown-linux-gnu` and
`aarch64-apple-darwin`. Each one gets an archive — a zip on Windows, a `.tar.gz`
on the other two — holding the binary, `LICENSE`, `NOTICE`, `README.md`,
`CHANGELOG.md` and a CycloneDX bill of materials. `README.md` travels with it
because a binary and a licence with no statement of what the thing is leaves the
person who unpacks it a year later with nothing to read.

The tag is not taken at its word. Before anything expensive runs, the workflow
checks that the tag, the `version` in `Cargo.toml` and a heading in
`CHANGELOG.md` all name the same version, and stops if they disagree: a release
nobody can describe afterwards is not worth the twenty minutes. It then runs the
test suite in the release profile on each of the three runners, because a tag
can point at a commit CI never saw, and `cargo deny` is asked again in a job of
its own, because a tag can be cut from a commit older than the newest advisory.
`NOTICE` is regenerated and the run fails if the result differs from what is
committed — on the Linux leg only, since that is the one whose registry cache
holds every target the file has to describe.

Windows additionally gets an NSIS installer, `vantage-<version>-setup.exe`,
which is what most people on Windows will download rather than the zip. It
installs per user, into `%LOCALAPPDATA%\Programs\Vantage`, so it never asks for
an administrator and touches nothing outside that account; it registers with
Add/Remove Programs under `HKCU`, so it can be found and removed the ordinary
way; and uninstalling asks before it deletes your dashboards, settings and logs,
with No as an answer that leaves them for a later install.

Every asset, the installer included, is published with a `.sha256` beside it.
**The binaries are not code signed**, so Windows warns about them and macOS
refuses them until they are notarised; that needs a certificate rather than a
change here, and until there is one the checksum is the only thing you can
check a download against. The release itself is created as a draft, so someone
reads the notes and the file list before it becomes something people download.

## Testing

565 tests as this is written — 520 beside the code they cover, two in `main.rs`,
and 43 in the files under `tests/` that drive the assembled program. That is a
fact about one commit rather than a property of the project: `cargo test` prints
the current number, and where it disagrees with this line it is this line that
is wrong.

The files under `tests/` are the ones that exercise the seams. They seed the
estate and resolve every dashboard's variables, assert that every shipped panel
returns data, check that the alerting console is legible, that it fires where
the incident is, and that it keeps evaluating while the window is hidden and
nothing is being drawn, hold the query engine to the places where it agrees and
deliberately disagrees with Prometheus about a failed scrape, check that every
setting the interface offers is read by something that draws rather than merely
saved, check that the simulator's live tick continues its counters instead
of restarting them, and hold the two paths by which an older build used to
destroy a newer one's work: `Ctrl+S` over a state file this build is too old to
read, and a field added by a later release surviving a round trip through this
one rather than being quietly dropped.

The suite runs in both profiles, because they are not the
same program: overflow checks are on only in the development profile and
`panic = "abort"` applies only to the release one, so a defect can be a caught
panic in one and a lost session in the other. `cargo clippy --all-targets --all-features -- -D warnings`
is clean; note that clippy prints nothing for a crate it has already checked, so
a cached target directory can make a dirty tree look clean — `touch src/lib.rs`
first for a real answer. There is no `unsafe`.

CI runs the gates on Windows, Linux and macOS with `--locked`, checks that the declared
`rust-version` still builds the tree, runs `cargo deny` for advisories and the
licence policy in `deny.toml`, and asserts that an unknown command-line argument
exits non-zero.
